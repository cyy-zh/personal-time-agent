# Personal Time Agent — 最终完整产品方案与验收要求

## 一、产品定位

开发一款运行于 ColorOS 16 的个人 AI 时间管理 Agent。

产品采用本地优先（Local-first）架构，以 AI Agent 为核心，集成任务管理、智能排程、长期目标管理、习惯管理、时间统计、手机行为分析和主动提醒等完整能力。

**只开发一个功能齐全的最终版本，不按 V1、V2、V3 分割功能。**

所有功能应采用模块化架构。用户能够根据个人需要开启或关闭不同模块，尤其可以自主决定是否下载安装和运行本地视觉 AI 模型。

应用应尽量减少用户管理任务和记录时间的操作负担。

### 产品目标

用户只需要通过自然语言告诉 Agent 想完成什么，Agent 就能：

1. 理解并记录任务。
2. 自动估计任务耗时。
3. 结合课表和已有日程安排执行时间。
4. 设置提醒并动态调整。
5. 管理跨越数周、数月的长期目标。
6. 安排运动、冥想、早睡等重复习惯。
7. 记录学习、科研、运动、娱乐等领域的实际投入时间。
8. 统计手机整体使用情况。
9. 在用户授权并启用本地模型后，进一步识别微信等 App 内部的具体活动。
10. 根据长期记录学习用户的时间偏好，优化未来安排。
11. 通过桌面 Widget 和完整 APP 与用户交互。

---

## 二、总体系统架构

采用一个独立 Android APP，内部划分为以下模块：

| 模块 | 主要职责 |
|---|---|
| Agent Core | 自然语言理解、决策、调用工具、协调其他模块 |
| Task Manager | 任务、子任务、优先级和截止日期管理 |
| Scheduling Engine | 时间安排、冲突检查、动态重排 |
| Goal & Habit Manager | 长期目标、早睡、运动、冥想等习惯管理 |
| Time Ledger | 实际活动时间记录和分类统计 |
| App Usage Monitor | Android 应用使用时长统计 |
| Activity Recognition | 可选的应用内部活动识别 |
| Local AI Runtime | 可选的本地视觉模型推理引擎 |
| Notification Collector | 可选的微信、QQ 等通知采集 |
| Reminder Engine | 本地提醒、后台唤醒和进度督促 |
| Memory & Analytics | 长期记忆、历史分析和个性化学习 |
| Android UI & Widget | APP 界面、桌面卡片和快速输入 |
| Local Database | 本地数据保存、备份和恢复 |

模块之间通过清晰的内部接口交换数据。

关闭任意可选模块，不应影响其他模块的正常运行。

### 基本架构原则

- 任务和时间数据以手机本地数据库为主要存储来源。
- 复杂 Agent 推理允许调用用户自定义的大模型 API。
- 普通时间调度、统计和提醒尽可能在本地完成。
- 不依赖电脑持续开机。
- 不依赖云服务器持续运行。
- 不依赖厂商推送才能执行普通本地提醒。
- 不要求 Root 或 ADB 常驻。
- 不依赖 Google AI Edge Gallery 持续运行。
- 模型接口、采集接口和任务数据层相互独立。
- 不允许 AI 直接绕过权限检查修改重要用户数据。

## 三、模块化开关机制

这是最终版本的核心设计要求。

APP 应在设置中提供统一的功能管理页面。

### 3.1 功能开关

至少包含：

| 功能 | 能否关闭 | 关闭后的行为 |
|---|---|---|
| AI 任务规划 | 可以 | 保留手动任务与日历 |
| 长期目标管理 | 可以 | 已有目标数据保留 |
| 习惯管理 | 可以 | 停止相关自动安排 |
| 手机使用统计 | 可以 | 停止新的使用统计采集 |
| 微信/QQ 通知采集 | 可以 | 停止监听与保存 |
| 应用内部活动识别 | 可以 | 保留普通 App 使用统计 |
| 本地视觉模型 | 可以 | 模型停止推理并释放资源 |
| 自动截图分析 | 可以 | 不再请求截图 |
| 主动 AI 复盘 | 可以 | 不再主动调用 AI |
| 普通任务提醒 | 可以 | 按用户选择关闭提醒 |

用户可以随时查看各模块状态。

### 3.2 本地视觉模型的三种状态

**状态 A：未安装**

- APP 不强制下载模型。
- 不占用额外的模型存储空间。
- 其他功能正常工作。
- 不执行视觉分析。

**状态 B：已安装但关闭**

- 模型文件可以保留。
- 不加载模型至内存。
- 不执行后台视觉推理。
- 不因为模型存在而持续消耗推理资源。
- 用户可以选择删除模型文件。

**状态 C：已安装并启用**

- 用户可以配置允许分析的 App。
- 在满足授权和运行条件时进行活动识别。
- 模型按需加载与卸载。
- 根据设备负载限制采样和推理频率。
- 自动记录识别结果、置信度及时间范围。

即使模型已经启用，也必须允许用户独立关闭自动截图采集。

### 3.3 权限与开关的关系

功能开关不能代替系统权限。

例如，开启“应用内部活动识别”后，仍应检查 Android 无障碍权限和相关截图能力。

权限未授权时：

- 明确提示缺少的能力。
- 提供正常授权入口。
- 不绕过系统限制。
- 不假装已经启用采集。
- 保留其他正常功能。

关闭采集模块后，应立即停止新的采集工作，不继续偷偷记录活动。

## 四、AI Agent 与自然语言交互

### 4.1 一句话创建任务

用户可以输入：

- “周五之前完成实验报告。”
- “明天下午整理科研数据。”
- “这周找时间复习半导体物理。”
- “未来一个月每周运动三次。”
- “以后每天尽量在 23:00 前上床。”

Agent 应自动区分一次性任务、重复习惯和长期目标。

根据具体意图创建相应的数据记录。

### 4.2 默认文字输入

文字输入是主要交互方式。

用户可以直接使用系统输入法自带的语音转文字功能，不要求 APP 独立开发语音识别引擎。

要求：

- 支持桌面快速输入。
- 支持自然语言创建和修改任务。
- 支持文字对话调整安排。
- 支持复制、粘贴和系统输入法。
- 在模型 API 不可用时保留待处理指令。

### 4.3 自由模型 API

允许配置：

- API 地址。
- API Key。
- 模型名称。
- 模型服务商。
- 必要的模型参数。

支持切换不同 AI 模型。

AI 服务商变化不能影响本地任务、长期记忆和历史统计。

本地视觉模型与负责规划的语言模型应当是独立配置项。

## 五、任务管理与智能时间规划

### 5.1 任务数据

每项任务至少记录：

- 名称。
- 类型。
- 重要程度。
- 真实截止日期。
- 计划完成日期。
- 计划执行时间。
- 预计耗时。
- 实际耗时。
- 完成状态。
- 关联长期目标。
- 提醒设置。
- 必要的来源信息。

必须区分真实截止日期与 AI 建议时间。

### 5.2 自动排程

Agent 应根据以下因素分配时间：

- 课程表。
- 已锁定日程。
- 任务重要性。
- 截止日期。
- 预计持续时间。
- 长期目标。
- 习惯安排。
- 睡眠时间。
- 用餐与休息。
- 历史效率和个人偏好。
- 当前用户状态。

不得生成违反硬约束的计划。

无法完成全部任务时，应主动说明时间不足，并提出调整方案。

### 5.3 动态重新规划

用户可以直接说：

- “这个任务已经完成了。”
- “我还需要一个小时。”
- “刚吃完晚饭，安排轻松一点的事情。”
- “今天不想做科研。”
- “帮我调整今天剩余的计划。”

Agent 应更新任务状态，重新计算未来安排并修改相应提醒。

### 5.4 受约束的自主权

Agent 可以自动调整普通任务计划，但以下行为必须请求确认：

- 修改真实截止日期。
- 移动锁定课程或活动。
- 侵占用户保护的睡眠时间。
- 删除重要历史数据。
- 放弃重要长期目标。
- 改变敏感信息采集权限。

所有重要操作必须可追溯、可撤销。

## 六、长期目标与习惯管理

### 6.1 长期目标

支持建立跨越数周或数月的目标，例如：

- 未来四周每天尽量早睡。
- 每周运动三次。
- 每周冥想四次。
- 每周学习不少于 30 小时。
- 每周为科研安排一定时间。
- 减少短视频使用。
- 长期准备考试和科研项目。

Agent 应将长期目标分解为阶段性安排。

### 6.2 智能习惯安排

重复习惯不能只是固定时间提醒。

例如每周运动三次，Agent 应当根据课程和其他任务，寻找合适时间，并在出现冲突时重新安排。

### 6.3 目标统计

支持显示：

- 本周目标次数。
- 实际完成次数。
- 达成比例。
- 连续达成情况。
- 历史变化趋势。

### 6.4 早睡目标

能够记录目标就寝时间、实际就寝记录和晚间活动情况。

不得直接将手机息屏时间当成真实入睡时间。

允许用户提供实际就寝信息，或通过额外授权的数据源补充证据。

## 七、个人时间账本

### 7.1 时间分类

至少支持：

- 课程学习。
- 自主学习。
- 科研。
- 运动。
- 冥想。
- 工作。
- 社交。
- 娱乐。
- 短视频。
- 生活事务。
- 休息。
- 睡眠相关活动。
- 未知活动。

支持用户自定义分类。

### 7.2 实际时间记录

必须区分：

- 计划时间。
- 实际记录时间。
- 系统自动采集时间。
- AI 推断时间。
- 未知时间。

不能把计划学习两小时直接当成实际学习两小时。

支持用户主动开始、暂停和结束任务计时。

支持自然语言修正时间记录。

### 7.3 统计报表

支持每日、每周、每月和自定义周期统计。

展示：

- 各领域实际投入时间。
- 时间分布。
- 与上一周期的比较。
- 计划与实际差异。
- 长期目标的投入情况。
- 手机使用情况。

所有统计应当能够追溯数据来源。

不能对同一时段重复累加总时长。

---

## 八、手机使用情况统计

### 8.1 基础 App 使用统计

在用户授权后，通过 Android 正式支持的使用情况接口获取：

- 手机使用时长。
- 各 App 前台使用时间。
- 应用切换记录。
- 屏幕交互状态。
- 每日和每周使用趋势。

需要与 ColorOS 16 系统统计结果比较，确定统计精度。

### 8.2 应用使用时间不等于活动时间

例如：

微信使用 90 分钟，可能包含：

- 聊天。
- 处理学习事务。
- 浏览公众号文章。
- 观看视频号。
- 其他活动。

系统不能直接将微信时间归类为社交或短视频。

如果没有开启深度识别，则显示微信总使用时间，并允许用户手动分类。

### 8.3 不使用本地模型时

必须仍然支持：

- App 级使用时间统计。
- 每日总使用时间统计。
- 每周使用趋势。
- 用户自定义分类。
- 手动纠错。
- 利用已知任务上下文提出候选分类。

但是，不得声称可以准确识别没有充分证据的应用内部活动。

## 九、可选的本地视觉活动识别引擎

这是完整最终版内置的可选高级功能。

### 9.1 目标

在用户启用后，识别指定 App 内部的具体活动，并计算相应的时间投入。

初始重点包括：

- 微信聊天。
- 微信群消息浏览。
- 微信视频号。
- 公众号文章阅读。
- QQ 聊天。
- 浏览器文章阅读。
- B站视频。
- 其他可以识别的活动。

识别机制必须可扩展，不能为每个 App 完全重写一套系统。

### 9.2 数据采集

在获得用户授权并符合系统权限要求时，可以综合使用：

- 应用前台状态。
- Android 使用情况事件。
- 无障碍界面事件。
- 可访问的界面文字和控件。
- 必要时的屏幕截图。
- 页面切换和滑动等行为线索。

优先利用轻量的系统事件和规则。

只有在需要进一步判断时才调用视觉模型。

### 9.3 截图策略

用户开启自动视觉分析后，系统可以针对已授权 App 的前台活动进行周期性或事件驱动截图。

但必须满足：

1. 仅分析用户允许的 App。
2. 不在屏幕关闭时持续截图。
3. 不绕过 Android 的安全窗口保护。
4. 支持自定义截图间隔或自动采样。
5. 不能使用无限高频截图。
6. 优先在界面明显变化时采样。
7. 不允许为截图而主动操控其他 App。
8. 遇到截图失败应记录原因并降级。
9. 不得影响用户正常操作手机。
10. 应主动控制 CPU、内存和电池开销。

### 9.4 本地视觉模型

模型默认不作为安装 APP 的必要条件。

启用时可以下载适合设备的模型。

要求：

- 尽量在本地完成图像分类。
- 不默认把截图上传到云端。
- 支持模型下载、删除和更换。
- 显示模型存储占用。
- 显示模型是否正在运行。
- 支持按需加载与释放。
- 根据设备性能控制模型调用频率。
- 运行失败时不影响其他功能。

可以参考 Google AI Edge Gallery 的模型管理和推理实现。

正式 APP 应优先直接集成成熟的端侧推理运行库，而不是依赖 Gallery APP 持续运行。

如果模型不支持图像输入，不能把普通文本模型当成视觉模型使用。

具体运行库和模型由开发过程中的实测决定。

### 9.5 识别结果

每次活动识别应产生结构化结果，例如：

- 来源 App。
- 活动类别。
- 开始和结束时间。
- 判断依据。
- 置信度。
- 模型或规则来源。
- 是否经过用户确认。

不同时间段应能合并形成连续活动记录。

不应简单用“截图次数 × 截图间隔”计算活动时长，而应该结合应用切换、页面变化和采样边界估计持续时间，并标记可能的误差。

### 9.6 不确定性

如果无法识别，应归类为未知。

例如无法判断微信当前页面是文章还是短视频，不得强行给出分类。

系统应允许用户直接说：

“刚刚微信里的那十分钟是在刷视频号。”

Agent 应修改记录并用于未来优化。

### 9.7 隐私保护

- 截图默认只在内存中进行推理，处理后释放。
- 不默认保存原始截图。
- 不上传截图到第三方服务器。
- 允许排除指定 App。
- 默认排除支付、银行、密码等敏感界面。
- 用户可以随时暂停识别。
- 用户可以删除所有活动记录。
- 不启用模型时不得继续进行视觉截图采集。

## 十、微信与 QQ 通知待办识别

在用户明确授权后，监听微信和 QQ 实际发布的系统通知。

支持：

- 识别来源。
- 保存可访问的通知内容。
- 消息去重。
- AI 识别潜在任务。
- 提取截止日期。
- 生成候选待办。
- 与已有任务去重。
- 保留消息来源。
- 对不确定任务请求确认。

必须区分：

- 没有通知。
- 有通知但没有正文。
- 有包含正文的通知。

不承诺自动读取全部聊天历史。

通知采集与视觉活动识别是独立模块，可以分别开启或关闭。

## 十一、本地提醒与后台执行

### 11.1 本地提醒

使用 Android 正常支持的提醒机制。

要求：

- 自动创建提醒。
- 修改提醒。
- 取消旧提醒。
- 避免重复提醒。
- 任务完成后取消无效提醒。
- 检查通知和精确闹钟权限。
- 重启后恢复能够恢复的提醒。

不依赖厂商推送才能进行普通提醒。

### 11.2 后台执行

使用符合 Android 系统规则的后台执行机制。

不能假定开启后台活动权限就能无限运行。

普通提醒不需要持续运行模型。

本地视觉模型只在功能启用且满足条件时运行。

复杂 AI 推理应避免阻塞系统通知与本地任务处理。

### 11.3 省电策略

必须对不同功能分别管理资源。

- 桌面显示优先使用本地缓存。
- 普通提醒优先使用系统调度。
- 使用统计优先读取系统现有数据。
- 视觉识别按需运行。
- 模型关闭后不得继续产生推理开销。

---

## 十二、长期记忆与情境感知规划

### 12.1 长期记忆

Agent 应长期保存：

- 用户目标。
- 任务耗时。
- 历史完成情况。
- 时间偏好。
- 习惯记录。
- 活动时间分布。
- 用户对 AI 的纠错。
- 已有证据支持的行为规律。

必须区分真实记录与模型推断。

### 12.2 时间段适应

Agent 应逐渐学习：

- 哪些时段适合复杂学习。
- 哪些时段适合科研。
- 哪些时段适合简单事务。
- 什么时候容易拖延。
- 哪些任务耗时容易被低估。
- 什么时候更适合运动或冥想。

### 12.3 情境感知

Agent 可以结合：

- 当前时间。
- 课表。
- 用餐情况。
- 已完成任务。
- 用户主动反馈。
- 历史行为规律。

动态判断现在适合进行什么活动。

例如用户说：

“我刚吃完晚饭。”

Agent 应考虑是否需要暂时安排较轻松的任务或休息，而不是机械执行原计划。

但必须根据用户实际经验调整，不得把一般生活规律当成对个人已经证实的事实。

### 12.4 持续优化

系统应比较：

- 预计耗时与实际耗时。
- 推荐时间与实际完成情况。
- 自动分类与用户纠错。
- 习惯安排与实际达成情况。

长期优化排程策略。

需要报告样本数量和不确定性。

不能在没有证据的情况下声称 AI 已经了解用户的习惯。

## 十五、最终验收标准

最终交付的是一个功能完整的 APP，而不是仅包含部分模块的测试版本。

### 15.1 功能完整性

以下功能必须集成：

- 自然语言任务管理。
- 自由模型 API。
- 智能时间规划。
- 受约束的自主决策。
- 长期目标管理。
- 习惯管理。
- 个人时间账本。
- 手机应用使用统计。
- 可选跨应用活动识别。
- 可选本地视觉模型。
- 微信/QQ 通知待办识别。
- 长期记忆和个性化规划。
- 本地提醒。
- ColorOS 16 桌面 Widget。
- 离线使用。
- 数据备份和恢复。

### 15.2 模型开关测试

必须测试：

**测试 A：完全不下载本地视觉模型**

所有非视觉模块正常工作。

**测试 B：下载模型但关闭功能**

APP 不应持续加载模型，也不应自动进行视觉截图。

**测试 C：启用模型并授权活动识别**

能够在系统允许的范围内分析指定 App 的前台活动。

**测试 D：关闭模型**

立即停止新的模型推理任务，并在合理时间内释放运行资源。

**测试 E：删除模型**

模型文件可以清理，但已有任务、统计、目标和历史记录不受影响。

### 15.3 视觉识别准确性

使用人工标注的样本测试：

- 微信普通聊天。
- 微信视频号。
- 微信文章阅读。
- QQ 聊天。
- 浏览器阅读。
- 其他支持的 App 内部活动。

要求同时统计：

- 分类准确率。
- 分类覆盖率。
- 未知活动比例。
- 错误分类情况。
- 活动时长估计偏差。

在覆盖足够样本的前提下，高置信度分类准确率目标不低于 90%。

无法确定的活动必须允许归类为未知。

### 15.4 手机使用统计

连续至少七天记录 App 使用情况，并与 ColorOS 自带统计比较。

在统计口径一致的条件下，日使用时长误差目标控制在 10% 以内。

不允许将微信总时长直接统计成短视频时间。

### 15.5 后台提醒

在亮屏、息屏、后台进程回收和省电模式等条件下开展真机测试。

至少完成 20 次提醒测试。

在具备必要权限的可测试条件下，目标为至少 95% 的提醒在计划时间之后 3 分钟内可见。

测试不通过时必须记录实际限制。

### 15.6 自主权

对至少 30 个涉及权限边界的场景进行测试。

未经授权修改真实截止日期、锁定事件、睡眠保护时间或重要历史数据的次数必须为零。

### 15.7 数据可靠性

验证：

- 网络中断。
- AI API 失败。
- 应用异常退出。
- 手机重启。
- 模型切换。
- 模型删除。
- 功能开关变化。
- 数据恢复。

不得发生未解释的重要任务数据丢失。

### 15.8 资源消耗

重点检查本地视觉模型在开启与关闭时的区别：

- CPU 使用。
- 内存占用。
- 电池消耗。
- 手机发热。
- 推理延迟。
- 截图频率。
- 模型存储占用。

至少完成 24 小时完整使用测试及七天使用统计观察。

模型关闭后，不应存在持续视觉推理造成的额外负担。

## 最终产品目标

Personal Time Agent 应当是一款功能完整、可自主配置、能够长期使用的个人智能时间管理应用。

它既要理解用户未来想做什么，也要记录用户过去实际做了什么，并利用长期积累的真实数据持续优化安排。

用户能够自主选择是否启用本地视觉模型、是否分析微信等 App 内部活动、是否监听聊天通知。

**关闭本地模型不会破坏基础时间管理能力，启用本地模型则可以获得更精细的活动识别与时间分析。**

所有功能统一集成于一个 Android APP 中，以本地数据、自由模型 API、可靠提醒、动态规划和用户控制权为核心原则。
